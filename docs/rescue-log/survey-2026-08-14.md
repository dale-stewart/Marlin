# Survey: what is left, measured (2026-08-14)

Taken because the last survey covered `Marlin/src/feature/` months ago, and picking the next
target from memory is how a rescue ends up re-treading well-covered ground. This is the evidence
base for choosing, not a plan.

Part of the rescue log — see [README.md](README.md) for the index.

## The denominator first

**128 of 799 non-HAL source files are compiled by at least one of the fourteen configurations.
671 are dark in all of them.**

Measured rather than inferred: each configuration was built and its object files listed, and the
union taken. (A first pass reported 799 of 799 dark, from a path-prefix mismatch, and a second
reported 145 compiled by counting 17 HAL files on one side only. Both were caught by arithmetic
that did not add up — `MarlinCore.cpp` cannot be dark, and 145 + 671 cannot be 799.)

So **every whole-tree percentage in this repository is over about a sixth of the tree**, and the
figure to quote alongside it is which configuration produced it. The default configuration
compiles 65 files that produce coverage data at all.

**Roughly two thirds of the dark code is display drivers**, and `dwin.cpp` has just put a number
on what testing those is worth: 65% line coverage bought 10.3% mutation, because four fifths of
the survivors are pixel coordinates that can only be killed by transcribing the code. Opening
another driver would repeat that trade at a larger scale. It is not the place to go next.

| `feature/powerloss.cpp` | `004-sd_powerloss` | 60% | 44 |
| `sd/Sd2Card.cpp` | `004-sd_powerloss` | **0%** | 206 |

Whole-configuration figures, for context: `001-default` 86.3%, `005-bed_leveling` 85.6%,
`003-extruders_3_runout` 81.3%, `004-sd_powerloss` 72.1%.

**`Sd2Card.cpp` at 0% is correct and is not a target.** Media is faked at the block device, not
at the wire: `DiskIODriver` is a pure virtual interface and `CardReader::changeMedia()` is public,
so the stand-in goes in at the level the firmware already abstracts. Testing `Sd2Card` would mean
implementing SD's command protocol to exercise code sitting well below anything a user can
observe. The 0% is a design decision that was already made, and it should not be read as a gap.

**`bed_leveling` has no gap of its own.** Its four largest are `temperature.cpp`,
`M17_M18_M84.cpp`, `gcode.cpp` and `queue.cpp` — all closed, all with their residue classified.
`probe.cpp` and `G29.cpp` turn out to be covered well enough not to appear.

## What that leaves

Ranked by value rather than by size:

1. **`feature/pause.cpp`** — 156 lines, 0%, compiled by two configurations and never executed.
   This is the filament change: park the nozzle, retract, wait for a person, purge, resume. It
   is the feature that touches a print mid-job, and every one of its failure modes ruins one —
   resuming at the wrong position, forgetting to re-heat, unparking into the part.
2. **`feature/e_parser.cpp`** — 69 lines, 0%. The emergency parser, which recognises `M108`,
   `M112` and `M410` in the serial stream *before* the queue, so a machine that is already stuck
   can still be stopped. `M112` is tested through `queue.cpp`'s reader; this is the other path
   and nothing reaches it. Small, and the consequence of it not working is the one that matters.
3. **`feature/binary_stream.h`** — 240 lines, 0%. Binary file transfer. Large, self-contained,
   and a protocol — which makes it good test material, but nothing about it is dangerous.
4. **`sd/SdBaseFile.cpp`** — 347 uncovered of 654. The largest absolute gap that is real, but it
   is FAT plumbing beneath a `cardreader.cpp` already at 79%, so the behaviour a user can reach
   is mostly covered from above.

Next target: **`feature/pause.cpp`**, with `e_parser.cpp` after it.
